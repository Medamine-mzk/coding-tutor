# Exercise cache with execution-verified matching and neverCache flag

Naive text-embedding matching merges "sum of a list" and "product of a list" despite near-identical phrasing, and an English-only embedder misses fr↔ar same-problem matches. Both would serve the wrong verified StepPlan.

Decision: platform-wide cache by default with a per-exercise `neverCache` boolean (Q1). Matching pipeline: 1) exact normalized-text hash, 2) embedding ANN (multilingual model covering fr/ar/en — LaBSE preferred for cross-lingual similarity until benchmarked vs mE5/BGE-M3 on the fr/ar/en library) in a second collection of the same vector store planned for hint retrieval (reuse, no new infra category; in-memory stub behind the same seam until that store exists per Q2), 3) for each candidate run the candidate's stored reference solution against the new submission's stated examples (whitespace/float/collection tolerance) — all match ⇒ merge. Only exact_hash and execution_verified auto-merge. No-examples case → one cheap LLM-judge on structured summaries, never auto-merge, log low-confidence to the single instructor-review surface (Q3: reuse the hint-review M6 queue, not a second queue). Concurrency via in-flight Map<normalizedHash, Promise>. Localization via `languages` map: translate display strings only, cache, no Stage A/B rerun. Version `step_plan_version` pinned per Session.

Hosting dependency (Q2 timing): the in-memory embedding index (`src/lib/exercise/exerciseCache.ts`) is a second collection behind the same seam. It fails safe — worst case is unnecessary regeneration, never a wrong merge, because only exact_hash and execution_verified auto-merge. On a persistent host (Render, Fly VM, or any single-node service) the Map survives between requests and the stub is fine to keep deferring; losing it only on redeploy is a non-issue. On Vercel-style serverless (stateless between invocations) the Map is empty on most cold starts, so the ANN candidate-narrowing tier barely functions and caching benefit is limited to exact_hash. That is still safe, but not much benefit until Qdrant/pgvector is real. Defer Qdrant/pgvector until hint-retrieval's vector store choice is locked, then reuse its collection — do not build a second store.

Why log-only for now: building a dedicated queue before we have data on low-confidence frequency is wasted work; the existing review surface is the same shape of problem.

Stage B / translation are not infra polish (see ADR 0006): Stage A (reference) already calls a real LLM (Gemini → Groq → Anthropic, `src/lib/exercise/reference.ts`) when keys are present, with heuristic fallback. Stage B decomposition (`src/lib/exercise/stepGenerator.ts`) now also tries the same LLM chain (Gemini 2.0 Flash first) and falls back to the heuristic milestone map if unavailable or verification fails; translation (`src/lib/exercise/localization.ts`) tries LLM and falls back to copy. In `NODE_ENV=test` / `VITEST` both intentionally use the heuristic/copy path for determinism. Vector-store benchmark (LaBSE vs mE5/BGE-M3) stays deferred — it is not on the critical path for correctness, while Stage B is.
